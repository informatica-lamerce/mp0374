01

Per què un servei de directori

Crear l'usuari una sola vegada i que serveixi a tots els equips i a totes les aplicacions.

Penseu en una empresa amb 40 ordinadors. Si cada equip té els seus usuaris locals (/etc/passwd a Linux, la base SAM a Windows), quan entra una persona nova cal crear-li el compte 40 vegades. Quan canvia la contrasenya, s'ha de canviar a cada equip. Quan marxa, cal recordar on tenia compte. No escala.

Un servei de directori guarda aquesta informació en un sol lloc: usuaris, grups, equips, impressores, telèfons... Els equips i les aplicacions li pregunten a ell. Es crea l'usuari una vegada i pot entrar a qualsevol equip o aplicació que consulti el directori. És l'acreditació centralitzada.

DirectoriBase de dades relacional
Es consulta molt més del que es modifica: cada inici de sessió és una lecturaLectures i escriptures equilibrades
Organització en arbre, com les carpetes d'un discOrganització en taules relacionades
Protocol estàndard (LDAP): qualsevol sistema o aplicació hi pot parlarCada producte té el seu connector i el seu dialecte SQL

Productes habituals: OpenLDAP, lliure, el que fareu servir; Active Directory de Microsoft, que combina LDAP, Kerberos i DNS; 389 Directory Server i FreeIPA, de Red Hat; i Samba AD, una implementació lliure d'Active Directory que veureu al RA6. Tots parlen LDAP.

L'EXEMPLE D'AQUESTES PÀGINES

Totes les ordres d'aquesta teoria es fan sobre un directori d'exemple: l'empresa Distribucions Exemple SL, amb el domini exemple.asix, un servidor ldap01 (192.168.50.10) i un client pc01 (192.168.50.20). A les pràctiques fareu el mateix amb el vostre domini, les vostres IP i el vostre cas d'empresa. No es tracta de copiar ordres, sinó d'entendre què canvia d'un cas a l'altre.

02

LDAP en poques idees

Un protocol client-servidor per consultar i modificar el directori.

LDAP (Lightweight Directory Access Protocol) és el protocol amb què els clients parlen amb el directori. Funciona sobre TCP:

URIPortÚs
ldap://389/tcpConnexió normal, sense xifrar. La que fareu servir a classe
ldaps://636/tcpConnexió xifrada amb TLS des del primer moment
ldapi:///—Socket local del servidor. Només des de la mateixa màquina; serveix per tocar la configuració

Les operacions que fa un client són poques:

OperacióQuè faOrdre
bindIdentificar-se davant del servidor, o entrar com a anònimldapwhoami i totes les altres
searchBuscar entradesldapsearch
addAfegir entradesldapadd
modifyCanviar atributs d'una entradaldapmodify, ldappasswd
deleteEsborrar una entradaldapdelete

En un bind anònim, el client no diu qui és, i el servidor només li deixa fer el que les seves regles permeten als anònims (normalment, llegir). En un bind autenticat, dona el nom complet d'una entrada (el seu DN, secció 3) i la contrasenya. El servidor decideix què pot fer cadascú amb les seves ACL (llistes de control d'accés, secció 7).

03

Com s'organitza la informació

Entrades, atributs i un arbre on cada entrada té un nom únic.

Cada objecte del directori (una persona, un grup, una unitat organitzativa) és una entrada. Una entrada és un conjunt d'atributs amb el format nom: valor. Alguns atributs poden tenir diversos valors, com mail o memberUid.

L'arbre: DIT

Les entrades s'organitzen en un arbre, el DIT (Directory Information Tree). A dalt hi ha l'arrel del domini. A sota, les unitats organitzatives (OU), que fan de carpetes. A les fulles, els usuaris, els grups i la resta d'objectes. L'arbre de l'empresa d'exemple:

dc=exemple,dc=asix
├── ou=Persones
│   ├── ou=Vendes
│   │   ├── uid=aprats        Anna Prats
│   │   └── uid=jgarcia       Jordi Garcia
│   └── ou=Magatzem
│       └── uid=mserra        Marta Serra
├── ou=Grups
│   ├── cn=comercials         gid 20001
│   ├── cn=magatzem           gid 20002
│   └── cn=encarregats        gid 20003
└── ou=Serveis
    └── uid=escaner           compte de servei

DN i RDN: el nom de cada entrada

Cada entrada té un nom únic, el DN (Distinguished Name). Es construeix des de l'entrada fins a l'arrel, separant els nivells amb comes. És com el camí complet d'un fitxer, però escrit al revés:

uid=aprats,ou=Vendes,ou=Persones,dc=exemple,dc=asix
└─ RDN ──┘ └──────────── DN del pare ─────────────┘

La primera part (uid=aprats) és l'RDN, el nom relatiu. Només ha de ser única dins del seu pare.

El DN base surt del domini

L'arrel, el DN base o sufix, es construeix a partir del nom DNS del domini: cada tros separat per punts és un dc (domain component). exemple.asix dona dc=exemple,dc=asix; empresa.cat donaria dc=empresa,dc=cat.

AtributNom completExemple
dcdomainComponentdc=asix
oorganizationo=exemple
ouorganizationalUnitou=Vendes
cncommonName: nom complet o nom del grupcn=Anna Prats, cn=comercials
uiduserid: nom per iniciar sessióuid=aprats
sn · givenNamecognom · nom de pilasn: Prats
04

L'esquema: objectClass i atributs

No es pot posar qualsevol atribut a qualsevol entrada.

L'esquema defineix quins tipus d'objecte existeixen (objectClass) i quins atributs té cadascun: uns d'obligatoris (MUST) i uns d'opcionals (MAY). Cada entrada té una classe estructural, que diu què és, i pot tenir classes auxiliars, que li afegeixen atributs.

objectClassTipusObligatorisOpcionals que fareu servir
organizationalUnitestructuraloudescription
posixGroupestructuralcn, gidNumbermemberUid, description
inetOrgPersonestructuralcn, sngivenName, mail, telephoneNumber, title, uid
posixAccountauxiliaruid, cn, uidNumber, gidNumber, homeDirectoryloginShell, userPassword
shadowAccountauxiliaruidcaducitat de la contrasenya

Un usuari que ha de poder iniciar sessió en un Linux porta tres classes: inetOrgPerson (la persona: nom, correu, telèfon), posixAccount (el compte Unix: UID, grup, home, shell) i shadowAccount. Un grup Unix és un posixGroup.

$ sudo ldapsearch -Q -LLL -Y EXTERNAL -H ldapi:/// -b cn=schema,cn=config -s one dn
dn: cn={0}core,cn=schema,cn=config
dn: cn={1}cosine,cn=schema,cn=config
dn: cn={2}nis,cn=schema,cn=config
dn: cn={3}inetorgperson,cn=schema,cn=config

Els esquemes que porta OpenLDAP a Ubuntu. nis té posixAccount i posixGroup; inetorgperson, inetOrgPerson.

Si falta un atribut obligatori, el servidor rebutja l'entrada i ho diu:

ldap_add: Object class violation (65)
	additional info: object class 'posixAccount' requires attribute 'uidNumber'
05

El format LDIF

Text pla per descriure entrades i canvis.

LDIF (LDAP Data Interchange Format) és el format que surt de slapcat i el que llegeixen ldapadd i ldapmodify. Normes:

  • Cada entrada comença per la línia dn:.
  • Després, una línia per atribut: nom: valor. Si un atribut té dos valors, s'escriu dues vegades.
  • Les entrades se separen amb una línia en blanc.
  • Les línies que comencen per # són comentaris.
  • Cap espai al final de les línies. És l'error més habitual i a l'editor no es veu.
  • Sense accents ni espais a uid i ou. Al cn, sí.

Afegir entrades

Un tros del fitxer base.ldif que crea l'arbre d'exemple. L'ordre importa: el pare sempre abans que el fill.

# Unitats organitzatives
dn: ou=Persones,dc=exemple,dc=asix
objectClass: organizationalUnit
ou: Persones

dn: ou=Vendes,ou=Persones,dc=exemple,dc=asix
objectClass: organizationalUnit
ou: Vendes

# Grup
dn: cn=comercials,ou=Grups,dc=exemple,dc=asix
objectClass: posixGroup
cn: comercials
gidNumber: 20001

# Usuari: persona + compte Unix
dn: uid=aprats,ou=Vendes,ou=Persones,dc=exemple,dc=asix
objectClass: inetOrgPerson
objectClass: posixAccount
objectClass: shadowAccount
uid: aprats
cn: Anna Prats
givenName: Anna
sn: Prats
mail: aprats@exemple.asix
uidNumber: 10001
gidNumber: 20001
homeDirectory: /home/aprats
loginShell: /bin/bash

No hi ha contrasenya: es posa després amb ldappasswd, que la guarda xifrada (secció 8).

Modificar entrades

Per canviar una entrada que ja existeix, el fitxer porta changetype: modify i una operació per atribut: add (afegir un valor), replace (substituir; si l'atribut no hi era, el crea) o delete (treure). Diverses operacions sobre la mateixa entrada se separen amb una línia que només té un guionet.

# mod.ldif
dn: uid=mserra,ou=Magatzem,ou=Persones,dc=exemple,dc=asix
changetype: modify
replace: loginShell
loginShell: /bin/bash
-
add: telephoneNumber
telephoneNumber: 934005566

dn: cn=encarregats,ou=Grups,dc=exemple,dc=asix
changetype: modify
add: memberUid
memberUid: mserra
UN NOM AMB ACCENT SURT COM A cn::

Quan un valor té caràcters que no són ASCII (accents, ç, ñ), ldapsearch i slapcat el mostren codificat en Base64 i amb dos punts dobles, per exemple cn:: TnXDunJpYSBSb2Nh. No és cap error: el valor està ben guardat. Per llegir-lo, echo TnXDunJpYSBSb2Nh | base64 -d, que dona Núria Roca.

Instal·lar el servidor OpenLDAP

De la màquina buida a un directori que respon, pas a pas.

L'exemple és el servidor ldap01, un Ubuntu Server 24.04. Com a l'aula, té dos adaptadors: el primer amb DHCP i sortida a internet, que no es toca, i el segon a la xarxa interna, on es posa la IP fixa.

Pas 1 · Nom i xarxa

$ sudo hostnamectl set-hostname ldap01
$ ip -br a                                   # el segon adaptador és el que no té IP
lo               UNKNOWN        127.0.0.1/8 ::1/128
enp1s0           UP             10.2.118.33/16 ...
enp2s0           UP

Un fitxer de netplan només per al segon adaptador. Netplan és molt estricte amb el sagnat: espais, mai tabuladors.

$ sudo nano /etc/netplan/60-interna.yaml
network:
  version: 2
  ethernets:
    enp2s0:
      dhcp4: false
      addresses: [192.168.50.10/24]
$ sudo chmod 600 /etc/netplan/60-interna.yaml
$ sudo netplan apply
$ ip -br a                                   # ara enp2s0 ha de tenir 192.168.50.10/24
$ echo "192.168.50.10 ldap01" | sudo tee -a /etc/hosts

Pas 2 · Instal·lar

$ sudo apt update
$ sudo apt install slapd ldap-utils

slapd és el servidor (Stand-alone LDAP Daemon); ldap-utils, les eines de línia d'ordres. La instal·lació només demana la contrasenya de l'administrador.

Pas 3 · Configurar el domini

La instal·lació crea el domini a partir del nom de la màquina i gairebé sempre acaba com a dc=nodomain. Es torna a obrir l'assistent complet:

$ sudo dpkg-reconfigure slapd

Just després d'instal·lar només hi ha l'arrel. Les OU, els grups i els usuaris encara no existeixen.

$ ldapwhoami -x -H ldap://localhost -D "cn=admin,dc=exemple,dc=asix" -W
Enter LDAP Password:
dn:cn=admin,dc=exemple,dc=asix

Si la contrasenya no és bona: Invalid credentials (49).

slapcat llegeix la base de dades directament del disc, sense passar pel protocol LDAP. Per això només funciona al servidor i amb sudo. Les altres eines passen per la xarxa i funcionen igual des del servidor que des del client.

ON ÉS L'ADMINISTRADOR?

A les versions actuals d'Ubuntu, cn=admin no és una entrada de l'arbre: és el rootDN definit a la configuració, amb la contrasenya a la mateixa configuració. Per això slapcat no el mostra, però ldapwhoami l'accepta. La secció següent ensenya on és.

07

Configuració i regles d'accés

L'arbre cn=config i qui pot llegir què.

QuèOnCom es toca
Configuració del servidorArbre especial cn=config, guardat a /etc/ldap/slapd.d/Amb ldapmodify via ldapi:///. No s'edita a mà
Dades del directori/var/lib/ldap/, base de dades MDBAmb les eines LDAP o amb LAM
AdministradorolcRootDN i olcRootPW de la base de dadesAmb dpkg-reconfigure slapd o ldapmodify

Al servidor, root pot llegir la configuració pel socket local amb -Y EXTERNAL: el servidor el reconeix pel fet de ser root a la mateixa màquina, sense contrasenya. Per veure la base de dades que té un sufix, amb tres dels seus atributs:

$ sudo ldapsearch -Q -LLL -Y EXTERNAL -H ldapi:/// -b cn=config "(olcSuffix=*)" olcSuffix olcRootDN olcAccess
dn: olcDatabase={1}mdb,cn=config
olcSuffix: dc=exemple,dc=asix
olcAccess: {0}to attrs=userPassword by self write by anonymous auth by * none
olcAccess: {1}to attrs=shadowLastChange by self write by * read
olcAccess: {2}to * by * read
olcRootDN: cn=admin,dc=exemple,dc=asix

Les tres línies olcAccess són les ACL per defecte. Es llegeixen en ordre i s'aplica la primera que encaixa:

ReglaQuè vol dir
{0} to attrs=userPassword by self write by anonymous auth by * noneCada usuari pot canviar la seva contrasenya. Un anònim la pot fer servir per autenticar-se, però ningú la pot llegir
{1} to attrs=shadowLastChange by self write by * readCada usuari pot actualitzar la data de canvi de contrasenya; els altres la poden llegir
{2} to * by * readTota la resta és de lectura per a tothom, també per als anònims

La regla 2 és la que permet que un client consulti el directori sense identificar-se. Va bé per aprendre, però en una empresa exposa noms, correus i telèfons a qualsevol que arribi al port 389.

09

Connectar un client Linux

NSS sap qui és l'usuari, PAM valida la contrasenya i nslcd ho pregunta al servidor.

Perquè un Ubuntu Desktop deixi entrar els usuaris del directori, han de passar dues coses:

  • NSS (Name Service Switch) ha de saber que existeixen: qui és aprats, quin UID té, quin grup, quin home. És el que consulten getent, id o ls -l.
  • PAM (Pluggable Authentication Modules) ha de validar la contrasenya quan inicien sessió.

Totes dues consultes passen per nslcd, un servei del client que fa d'intermediari amb el servidor.

pc01Inici de sessió, getent, id
NSS · PAM
nslcd/etc/nslcd.conf
uri i base
ldap01slapd
port 389

Pas 1 · Nom i xarxa del client

A Ubuntu Desktop, la xarxa la gestiona NetworkManager. Es pot fer des de Configuració → Xarxa, a la connexió del segon adaptador (IPv4 manual, sense porta d'enllaç ni DNS), o des del terminal:

$ sudo hostnamectl set-hostname pc01
$ nmcli con show                             # nom de la connexió del segon adaptador
$ sudo nmcli con mod "Wired connection 2" ipv4.method manual ipv4.addresses 192.168.50.20/24
$ sudo nmcli con up "Wired connection 2"
$ ping -c 3 192.168.50.10
$ echo "192.168.50.10 ldap01" | sudo tee -a /etc/hosts

Pas 2 · Paquets i assistent

$ sudo apt update
$ sudo apt install libnss-ldapd libpam-ldapd ldap-utils
PaquetQuè aporta
libnss-ldapdQue el sistema vegi els usuaris i grups del directori (NSS)
libpam-ldapdQue s'hi puguin autenticar (PAM)
nslcd (s'instal·la sol)El servei que fa les consultes al servidor

En instal·lar-los s'obre un assistent:

PreguntaResposta a l'exemple
LDAP server URIldap://192.168.50.10/
LDAP server search basedc=exemple,dc=asix
Name services to configurepasswd, group i shadow, marcats amb la barra espaiadora

Per tornar a obrir-lo: sudo dpkg-reconfigure nslcd (servidor i base) o sudo dpkg-reconfigure libnss-ldapd (serveis).

Pas 3 · Revisar els fitxers

$ grep -E "^(uri|base)" /etc/nslcd.conf
uri ldap://192.168.50.10/
base dc=exemple,dc=asix
$ grep -E "^(passwd|group|shadow)" /etc/nsswitch.conf
passwd:         files systemd ldap
group:          files systemd ldap
shadow:         files systemd ldap
$ sudo systemctl restart nslcd
$ systemctl status nslcd --no-pager          # active (running)

passwd: files systemd ldap vol dir: primer els fitxers locals i, si no el troba, el directori. nslcd només llegeix nslcd.conf en arrencar: després de canviar-lo, cal reiniciar-lo.

Pas 4 · Crear el home automàticament

Els usuaris del directori no tenen carpeta a /home del client. Sense ella, el login gràfic accepta la contrasenya i torna a la pantalla d'inici. El mòdul pam_mkhomedir la crea el primer cop que l'usuari entra:

$ sudo pam-auth-update --enable mkhomedir
$ grep mkhomedir /etc/pam.d/common-session
session optional                        pam_mkhomedir.so

Pas 5 · Comprovar

$ ldapsearch -x -LLL -H ldap://192.168.50.10 -b "dc=exemple,dc=asix" -s base dn
dn: dc=exemple,dc=asix
$ getent passwd | tail -3                    # amb el directori buit, només comptes locals

Si ldapsearch respon des del client, el client arriba al directori. Quan hi hagi usuaris (seccions 11 i 12), getent els mostrarà i s'hi podrà iniciar sessió.

ALTERNATIVA: SSSD

Ubuntu recomana SSSD per als clients LDAP i Active Directory. És més complet (guarda credencials en memòria cau, per exemple), però per defecte no accepta autenticació per LDAP sense xifrar. Per això en aquest RA es fa servir nslcd. SSSD apareixerà al RA6, quan unireu un Linux a un domini Samba AD.

10

Dissenyar el DIT

Primer es dibuixa l'arbre; després es construeix.

Canviar l'estructura un cop feta surt car: els DN canvien, i les aplicacions configurades amb una base de cerca deixen de trobar els usuaris (secció 14).

OrganitzacióAvantatgesInconvenients
Plana: tots els usuaris a la mateixa OUSimple. Ningú s'ha de moure quan canvia de departamentAmb molts usuaris es fa difícil de gestionar. No es pot fer res per departament a partir de la posició
Per departament: una OU per a cada unReflecteix l'empresa. Permet buscar o delegar per departamentSi una persona canvia de departament, canvia el seu DN
Per seu: una OU per a cada lloc físicÚtil quan cada seu té el seu administradorNo diu res de la funció de cada persona
Per tipus d'objecte: persones, grups, serveis...Les aplicacions poden buscar només on tocaPer si sola, no organitza les persones

A la pràctica es combinen. Una opció molt habitual és separar per tipus al primer nivell i per departament dins de les persones, com a l'empresa d'exemple.

Convencions

  • Nom d'usuari: inicial del nom + primer cognom, minúscules i sense accents (aprats). Si ja existeix, s'afegeix la segona lletra del nom (anprats).
  • Rangs: persones a partir de uidNumber 10001; grups a partir de gidNumber 20001; comptes de servei a partir de 10100. Els usuaris locals de cada Linux comencen pel 1000: si els rangs se solapen, un usuari del directori i un de local poden tenir el mateix número.
  • Home i shell: /home/uid i /bin/bash per a les persones.
LDAP NO VIGILA ELS NÚMEROS REPETITS

LDAP Account Manager: el directori des del navegador.

LAM és una aplicació web per gestionar usuaris, grups i unitats organitzatives sense escriure LDIF. S'instal·la al servidor (porta Apache i PHP) i s'hi entra des del navegador del client.

$ sudo apt install ldap-account-manager

Des del client: http://192.168.50.10/lam.

Filtres de cerca

Des d'on, fins on, què i quins atributs.

Una cerca amb ldapsearch té quatre parts: des d'on es busca (-b), fins a quina profunditat (-s), què es busca (el filtre) i quins atributs es volen veure, al final de l'ordre.

$ ldapsearch -x -LLL -H ldap://localhost -b "dc=exemple,dc=asix" -s sub "(objectClass=posixAccount)" uid cn

Sense atributs, els mostra tots. Sense filtre, fa servir (objectClass=*), que vol dir «tot».

Abast

AbastQuè inclouAmb -b dc=exemple,dc=asix
baseNomés l'entrada de la baseL'arrel i prou
oneEls fills directes de la basePersones, Grups i Serveis
subLa base i tot el que penja a sota. Per defecteTot l'arbre
 
$ ldapsearch -x -LLL -H ldap://localhost -b "dc=exemple,dc=asix" -s one dn
dn: ou=Grups,dc=exemple,dc=asix
dn: ou=Serveis,dc=exemple,dc=asix
dn: ou=Persones,dc=exemple,dc=asix

Sintaxi

FiltreSignificat
(uid=aprats)Igualtat
(telephoneNumber=*)Presència: té l'atribut, amb qualsevol valor
(sn=G*) · (cn=*Ser*)Comença per G · conté «Ser»
(uidNumber>=10002) · (uidNumber<=10002)Més gran o igual · més petit o igual. No existeixen > ni < sols
(&(A)(B))I: es compleixen totes les condicions
(|(A)(B))O: se'n compleix alguna
(!(A))NO: no es compleix

L'operador va davant de les condicions, no entre elles. Cada condició, entre parèntesis, i el filtre sencer també. El filtre sempre entre cometes dobles, perquè el shell no interpreti *, &, | o !.

Exemples sobre l'empresa d'exemple

Limitar-se a una branca: la base, no el filtre

Un filtre (ou=Vendes) no retorna les persones de Vendes: retorna l'entrada de la OU. Les persones no tenen atribut ou; la OU forma part del seu DN. Per buscar dins d'una branca, es canvia la base:

$ ldapsearch -x -LLL -H ldap://localhost -b "ou=Vendes,ou=Persones,dc=exemple,dc=asix" "(objectClass=posixAccount)" uid

Integrar el directori amb Apache

Una intranet on cada persona entra amb el seu usuari del directori.

Moltes aplicacions poden delegar l'autenticació al directori: servidors web, Nextcloud, GitLab, Moodle, el correu, la VPN, Samba... Cada persona té un sol usuari i una sola contrasenya, i quan marxa de l'empresa s'esborra en un sol lloc. Gairebé totes fan el mateix:

1. CercaAmb el nom escrit (aprats), busca el DN complet de l'usuari, com a anònim o amb un compte de servei.
2. BindEs connecta amb aquest DN i la contrasenya escrita. Si el servidor l'accepta, la contrasenya és bona. L'aplicació mai no llegeix la contrasenya.
3. AutoritzacióComprova si l'usuari, a més d'existir, té permís per a aquell recurs.

L'exemple: una intranet per a Distribucions Exemple a /var/www/html/intranet del servidor, amb aquestes zones:

ZonaQui hi entra
/intranet/Qualsevol persona del directori
/intranet/vendes/ · /intranet/magatzem/Les persones amb aquell grup principal
/intranet/encarregats/Els membres del grup transversal
/intranet/direccio/Només l'Anna
/intranet/telefons/Les persones de Vendes amb telèfon

Pas 1 · Activar el mòdul

Si al servidor hi ha LAM, ja hi ha Apache.

$ sudo a2enmod authnz_ldap                   # activa també ldap, del qual depèn
$ sudo systemctl restart apache2
$ apache2ctl -M | grep ldap

$ echo "<h1>Zona vendes</h1>" | sudo tee /var/www/html/intranet/vendes/index.html
$ find /var/www/html/intranet -name index.html

$ sudo nano /etc/apache2/conf-available/intranet-ldap.conf

DirectivaQui hi pot entrar

Require ldap-user aprats jgarciaEls usuaris de la llista, separats per espais
Require ldap-group cn=...Els membres del grup, segons l'atribut de AuthLDAPGroupAttribute
Require ldap-attribute gidNumber=20001Els usuaris amb aquest valor en aquest atribut

DOS DETALLS QUE FAN PERDRE MOLT DE TEMPS

1. ldap-group només mira memberUid. Per defecte, Apache busca els membres als atributs member i uniqueMember, amb DN complets. Els grups POSIX fan servir memberUid amb el nom curt; d'aquí AuthLDAPGroupAttribute memberUid i AuthLDAPGroupAttributeIsDN off. Tot i així, qui té el grup com a principal no és a memberUid: amb Require ldap-group cn=comercials,... ni l'Anna ni el Jordi entrarien. Per al grup principal, ldap-attribute gidNumber=....

2. ldap-filter va sense parèntesis exteriors i sense cometes. Apache hi afegeix els seus. Amb el filtre sencer entre parèntesis o entre cometes, no hi entra ningú.

Pas 7 · La contrasenya viatja en clar: HTTPS

Amb AuthType Basic, el navegador envia usuari i contrasenya a cada petició, només codificats en Base64. Codificar no és xifrar:

$ curl -sv -u aprats http://192.168.50.10/intranet/ -o /dev/null 2>&1 | grep Authorization
> Authorization: Basic YXByYXRzOlBhdGF0YTEyMw==
$ echo YXByYXRzOlBhdGF0YTEyMw== | base64 -d
aprats:Patata123

Qualsevol que capturi el trànsit veu la contrasenya. La solució és HTTPS. Ubuntu porta un lloc HTTPS preparat amb un certificat autosignat:

$ sudo a2enmod ssl
$ sudo a2ensite default-ssl
$ sudo systemctl reload apache2
$ curl -k -s -o /dev/null -w "%{http_code}\n" -u aprats https://192.168.50.10/intranet/

-k accepta el certificat autosignat. El navegador mostrarà un avís per la mateixa raó.

Perquè la intranet no funcioni per HTTP, una redirecció dins del <VirtualHost *:80> de /etc/apache2/sites-available/000-default.conf. No a default-ssl.conf, o es fa un bucle:

Redirect permanent /intranet https://192.168.50.10/intranet
$ sudo systemctl reload apache2
$ curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" http://192.168.50.10/intranet/
301 https://192.168.50.10/intranet/

El trànsit entre Apache i slapd també va en clar pel port 389. Aquí no importa, perquè tots dos són a la mateixa màquina. Si fossin a màquines diferents, caldria ldaps:// o StartTLS.

Les pràctiques del RA1
